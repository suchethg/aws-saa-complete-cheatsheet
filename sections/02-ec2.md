# **EC2 — Elastic Compute Cloud & Shared File Storage**

EC2 provides virtual compute resources in the cloud. The SAA exam heavily tests compute options alongside storage choices (EBS, EFS, Instance Store, FSx) for specific performance and architectural patterns.

---

## **EC2 Instance Families — Know Which to Pick**

| Family | Optimized For | Use Cases | Memory Aid |
| ----- | ----- | ----- | ----- |
| General Purpose (T, M) | Balanced CPU/Memory/Network | Web servers, dev/test, small DBs | T = Tiny/Burstable; M = Most balanced |
| Compute Optimized (C) | High CPU | Batch processing, HPC, gaming servers, ML inference | C = CPU crunching |
| Memory Optimized (R, X, z, u) | High RAM | In-memory DBs (Redis), SAP HANA, big data analytics | R = RAM; X = eXtra RAM |
| Storage Optimized (I, D, H) | High I/O throughput | NoSQL DBs, data warehousing, Hadoop, OLAP | I = IOPS; D = Dense storage |
| Accelerated (P, G, F, Inf, Trn) | GPU / FPGA / AI chips | ML training, video transcoding, HPC, genomics | P/G = GPU; Inf/Trn = AI chips |

## **EC2 Purchasing Options — THE Most Common SAA Decision**

| Option | Discount vs On-Demand | Commitment | Best For | Exam Keyword |
| ----- | ----- | ----- | ----- | ----- |
| On-Demand | 0% (baseline) | None | Short-term, unpredictable workloads | "short-term", "unpredictable", "testing" |
| Reserved (Standard) | Up to 72% | 1 or 3 years | Steady-state predictable workloads | "steady state", "always running", "known load" |
| Reserved (Convertible) | Up to 66% | 1 or 3 years | Same but need to change instance type | "need flexibility", "might change instance" |
| Savings Plans (Compute) | Up to 66% | 1 or 3 years | Flexible: auto applies to EC2, Fargate, Lambda | "most flexible", "Lambda + EC2 mix" |
| Spot Instances | Up to 90% | None (can be interrupted) | Fault-tolerant, batch, stateless workloads | "fault tolerant", "batch", "cheapest" |
| Dedicated Hosts | On-Demand price or Reserved | Optional 3yr | Compliance, bring-your-own-license (BYOL) | "BYOL", "compliance", "per-socket licensing" |
| Dedicated Instances | ~10% premium | None | Hardware isolation without managing host | "hardware isolation", "not share with others" |

| ⚠️ EXAM TRAP: Dedicated Hosts vs Dedicated Instances: Hosts give you control of the physical server (socket/core visibility for BYOL). Dedicated Instances just mean your VMs don't share hardware with other AWS customers — but you don't control the host. |

## **EC2 Networking & Outbound Internet Egress**

| Networking Gateway | Traffic Protocol | How It Works | Key Exam Scenario |
| ----- | ----- | ----- | ----- |
| **NAT Gateway** | **IPv4 ONLY** | Translates private IPv4 addresses to a public Elastic IP. Resides in public subnet. | "Private subnet IPv4 instances need internet access for software patches" |
| **Egress-Only Internet Gateway (EIGW)** | **IPv6 ONLY** | Stateful gateway for IPv6. Allows outbound IPv6 traffic while blocking inbound connections. | "Private subnet IPv6 instances need outbound-only internet connectivity" |
| **Internet Gateway (IGW)** | **IPv4 & IPv6** | Allows bi-directional communication to/from the internet. Associated with public subnets. | "Public-facing EC2 instances requiring inbound and outbound traffic" |

| ⚠️ EXAM TRAP: NAT Gateway vs Egress-Only IGW: NAT Gateway does **NOT** work for IPv6 traffic! If the exam explicitly specifies **IPv6** outbound-only communication, the answer is ALWAYS **Egress-Only Internet Gateway**. |

| Storage Type | Type | Persistence | Max IOPS | Use Case | Key Facts |
| ----- | ----- | ----- | ----- | ----- | ----- |

## **EFS (Elastic File System) — Deep Dive**

Amazon EFS provides a fully managed, scalable, highly available, **POSIX-compliant** shared file system designed for Linux workloads using **NFSv4**.

### **EFS Key Characteristics**
* **Multi-AZ Shared Access:** Simultaneously accessible by thousands of EC2 instances, ECS tasks, or Lambda functions across multiple Availability Zones.
* **Storage Protocol:** Uses NFSv4 protocol (Linux native). **Not for Windows OS** (use FSx for Windows for SMB/Windows).
* **Consistency & Locking:** Supports strong consistency and file locking essential for Content Management Systems (CMS like WordPress/Drupal) and shared web application assets.

---

### **EFS Performance Modes**

| Mode | Behavior | Best Used For |
| ----- | ----- | ----- |
| **General Purpose** (Default) | Ideal for latency-sensitive workloads with low per-file latency. | Web servers, CMS, developer tools, general file shares. |
| **Max I/O** | Scales to higher overall throughput and IOPS (100k+) at the expense of slightly higher latency per metadata operation. | Large-scale parallel processing, HPC, big data, hundreds of concurrent containers/tasks. |

---

### **EFS Throughput Modes**

| Mode | Behavior | Best Used For |
| ----- | ----- | ----- |
| **Bursting Throughput** (Default) | Throughput scales with total file system size (50 KiB/s per GiB stored). Accumulates burst credits. | Workloads with spiky traffic (high throughput short bursts, low rest). |
| **Provisioned Throughput** | Define fixed throughput (MiB/s) independent of storage size. | Small datasets (< 1 TiB) that require high, sustained throughput demands. |
| **Elastic Throughput** | Auto-scales throughput dynamically based on workload demands. Pay strictly per read/write MiB. | Unpredictable applications with variable throughput spikes. |

---

### **EFS Storage Classes & Lifecycle Management**

* **EFS Standard / Standard-Infrequent Access (IA):** Regional multi-AZ durability.
* **EFS One Zone / One Zone-IA:** Single-AZ deployment for 47% cost savings (non-critical/recreatable data).
* **Lifecycle Management:** Automatically moves unaccessed files (e.g., after 30 or 60 days) to IA storage classes to minimize storage costs.

| ⚠️ EXAM TRAP: EBS Multi-Attach vs EFS: **EBS Multi-Attach** (io1/io2 only) attaches an EBS volume to multiple instances **in the SAME AZ** and requires a cluster-aware file system. **EFS** natively spans **MULTIPLE AZs**, requires no cluster software, and uses standard NFSv4. |

## **EC2 High Availability & Auto Scaling**

### **Auto Scaling Group (ASG) Policies**

| Policy Type | How it Works | Best For | Exam Scenario |
| ----- | ----- | ----- | ----- |
| Target Tracking | Maintains a metric at target (e.g. CPU = 50%) | Most workloads; simplest | "keep CPU at 40%" |
| Step Scaling | Adds/removes capacity in **tiered steps** based on alarm breach thresholds | Tiered response to demand spikes | "add 1 instance at 50% CPU, add 3 instances at 80% CPU" |
| Simple Scaling | Single adjustment per alarm; obeys **Cooldown Period** | Legacy rules | Single metric trigger; wait for cooldown |
| Scheduled Scaling | Scale on cron schedule | Predictable load patterns | "traffic spikes every Monday 9am" |
| Predictive Scaling | ML forecasts future load; scales proactively | Cyclical workloads | "prevent under-provisioning before spike" |

### **Cooldown Period vs Default Instance Warmup**

| Concept | What it Does | Default Value | Key Exam Detail |
| ----- | ----- | ----- | ----- |
| **Default Cooldown** | Pauses additional Simple Scaling actions after scaling completes | **300 seconds** | Ensures newly launched/terminated instances stabilize metrics |
| **Default Instance Warmup** | Applies to Target Tracking & Step Scaling | Null (falls back to Cooldown) | Prevents Step/Target Tracking from over-scaling while new instances boot |

## **EC2 Placement Groups**

| Strategy | Behavior | Use Case | Limitation |
| ----- | ----- | ----- | ----- |
| Cluster | All instances in same AZ, same rack — ultra-low latency | HPC, tightly coupled distributed computing | Risk: single rack failure takes all instances. Cannot span AZs. |
| Spread | Each instance on distinct hardware — max 7 per AZ | Critical instances surviving hardware failure (Kafka, ZooKeeper) | Max 7 instances per AZ — hard limit |
| Partition | Groups of instances on separate racks; up to 7 partitions/AZ | Distributed databases (Cassandra, Hadoop) needing rack awareness | Instances in same partition share rack risk |

| 🧠 MNEMONIC: CSP = Cluster (Speed), Spread (Safety), Partition (Scale-Safety). |
